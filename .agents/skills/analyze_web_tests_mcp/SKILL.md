# Analyzing Web-Tests Results with the MCP Server

The `web-tests-analyzer` MCP server (`analysis/mcp/mcp.js`, shared core in `analysis/common/`) provides statistical comparison tools over `metrics.json` files produced by `cuj/crossbench/runner/run.py` (via `gather_metrics.py`).

## 1. How `metrics.json` Datasets Are Structured

When `run.py` finishes executing tests, `cuj/crossbench/runner/runner/gather_metrics.py` compiles two sources of data from every pass into `<results_dir>/metrics.json`:
1. **Press Benchmark JSON Probes** (`speedometer_3.1`, `jetstream_2.2`, `motionmark_1.3`, `loadline2-tablet`).
2. **Perfetto Trace Summaries (`v2_metrics.pb`)** generated by Perfetto `trace_processor` from `cuj/crossbench/common-metrics/*.textproto` and per-CUJ `metrics.textproto`.

Each entry in `metrics.json` has the form:
```json
{
  "test_name": "docs",
  "variant": "",
  "browser": "chrome_v150",
  "metric": "cuj.uma.lower_is_better-EventLatency.TotalLatency-p90",
  "values": [42150.0],
  "units": "unknown",
  "improvement_direction": "down"
}
```
- When `variant` is non-empty and not `"default"`, `parseDataset()` formats the test name as `"<test_name> (<variant>)"` (e.g., `"tab-stress (heavy)"`, `"meet-note (4p)"`).
- Multiple runs/iterations in the same `metrics.json` (or across multiple `metrics.json` paths in the same `datasetGroup`) have their `values` arrays concatenated into a single sample distribution per `(testName, metricName)`.

## 2. Available MCP Tools (`web-tests-analyzer`)

All dataset-accepting tools take a `datasetGroups` array where **Group 0 is the baseline** and **Groups 1..N are compared against Group 0**:
```json
{
  "datasetGroups": [
    {
      "name": "Baseline",
      "paths": ["/path/to/baseline_run/metrics.json"]
    },
    {
      "name": "Candidate",
      "paths": ["gs://bucket/path/to/candidate_run/metrics.json"]
    }
  ]
}
```

### Tool Reference

1. **`get_dataset_metadata`**
   - **Purpose**: Extracts hardware, OS, browser version (`cr_version`, `cr_revision`), build fingerprint (`android_build_fingerprint`), hardware class (`hardware_class`), and system RAM (`system_ram_bytes`, `cr_physical_memory`) for each group.
   - **Always call this first** to verify that the baseline and candidate datasets match on expected dimensions (e.g., same Chrome version and build ID).

2. **`compare_datasets`**
   - **Purpose**: Lists `baselineTests` (all test names present in Group 0) and `mismatches` (any tests missing from either group).
   - **Call this second** to see the exact test names (including variant suffixes like `"tab-stress (heavy)"`) available for analysis.

3. **`get_important_metrics`**
   - **Arguments**: `{ "testName": "<test_name>" }`
   - **Purpose**: Returns the curated list of headline metrics for `<testName>` from `analysis/common/important_metrics.js` (matched by longest prefix of `testName`).

4. **`get_significant_changes`**
   - **Arguments**:
     - `datasetGroups` (required): Array of dataset groups.
     - `testName` (optional): Name of a specific test (or omit to scan **all** common baseline tests in a single call).
     - `aggMode` (optional): `"all" | "avg" | "p50" | "p90" | ...`
     - `importantMetrics` (optional): Custom array of metric substring filters.
     - `searchQuery` (optional): Case-insensitive substring filter across all metrics.
     - `displayAll` (optional): When `true`, checks all metrics instead of only `importantMetrics`.
     - `includeRawSignificant` (optional): When `true`, also includes metrics with raw `pValue <= 0.05` (`rawSignificant === true`), which is essential for small-sample runs ($N \le 5$).
   - **Purpose**: Analyzes one or all common tests and returns metrics with a statistically significant change, along with `summary` counts (`totalRegressions`, `totalImprovements`, `totalRawRegressions`, `totalRawImprovements`).

5. **`analyze_test`**
   - **Arguments**:
     - `testName` (required): Name of the test (e.g., `"docs"`, `"browsing-multitab"`).
     - `datasetGroups` (required): Array of dataset groups.
     - `aggMode` (optional): Filter aggregated metrics (`"all"`, `"avg"`, `"max"`, `"min"`, `"p50"`, `"p75"`, `"p90"`, `"p95"`, `"p99"`, `"sum"`, `"count"`, `"stddev"`).
     - `importantMetrics` (optional): Custom array of metric substring patterns to retrieve.
     - `searchQuery` (optional): Case-insensitive substring search across all metrics in the test (automatically enables `displayAll: true` when `importantMetrics` is not set).
     - `displayAll` (optional): When `true`, returns all metrics in the test instead of filtering to `importantMetrics`.
   - **Critical Pro-Tip (`searchQuery` and `importantMetrics`)**:
     By default, if `searchQuery`, `displayAll`, and `importantMetrics` are omitted, `analyze_test` only returns metrics listed in `important_metrics.js` for that test.
     To query deep-dive subsystem metrics (such as `meminfo`, `lmk_kill_count`, `Memory.Renderer.PrivateMemoryFootprint`, `Discarding.DiscardLatency`, `percent_inputs_slower_than`), pass `searchQuery` (e.g., `searchQuery: "meminfo"`) or pass custom substring patterns in `importantMetrics`:
     ```json
     {
       "testName": "docs",
       "datasetGroups": [...],
       "importantMetrics": [
         "meminfo",
         "lmk_kill",
         "Memory.",
         "Discarding.",
         "Browser.Tabs.TotalSwitchDuration3",
         "percent_inputs_slower_than",
         "EventLatency.TotalLatency"
       ]
     }
     ```

6. **`analyze_all_tests`**
   - **Arguments**: `{ "datasetGroups": [...], "aggMode": "...", "searchQuery": "...", "displayAll": false }`
   - **Purpose**: Runs `analyze_test` across all common baseline tests and aggregates total significant and raw-significant regressions/improvements.

## 3. Recommended Agent Workflow for Dataset Analysis

1. **Step 1 — Verify Environment & Test Inventory**:
   - Call `get_dataset_metadata` and `compare_datasets`.
   - Confirm `system_ram_bytes`, `hardware_class`, `android_build_fingerprint`, and `cr_version`.
2. **Step 2 — High-Level Triage Across Core Metrics**:
   - Call `get_significant_changes` (omitting `testName` to scan all common tests), or call `analyze_test` with `aggMode: "avg"` and `aggMode: "p90"`.
3. **Step 3 — Subsystem Deep-Dive via `importantMetrics` Substring Matching**:
   - Pass targeted `importantMetrics` substrings to `analyze_test` to pull memory, LMK, tab-discard, slow-input, and CPU metrics across CUJs:
     - Memory & Swap: `["meminfo", "Memory.", "heap_total"]`
     - Tab Discards & Kills: `["lmk_kill", "Discarding.", "Tabs.TotalSwitchDuration3", "Tabs.TabSwitchResult3", "tabs_alive", "total_renderers"]`
     - Input & Tail Latency: `["percent_inputs_slower_than", "num_inputs_slower_than", "EventLatency.", "InputDelay3", "ScrollJank"]`
     - Smoothness & Graphics: `["PercentDroppedFrames", "Jank3", "Checkerboarding", "GpuBusyDuration", "gpu_context_cleanup"]`
     - CPU Contention: `["cpu_usage_stat", "cpu.times"]`

## 4. Statistical Nuances & Caveats to Keep in Mind

When interpreting `pValue` and `significant` from the MCP server (`analysis/common/stats.js` and `analyzer.js`):

1. **Two-Tailed Permutation Test Floor for Small Sample Sizes ($N \le 5$)**:
   - `permutationTest(leftVals, rightVals)` enumerates all $\binom{N_1 + N_2}{N_1}$ exact splits when $\binom{N_1 + N_2}{N_1} \le 5000$.
   - For a **5 vs 5** run, there are $\binom{10}{5} = 252$ splits. Even if every single value in Group 2 is 10x worse than Group 1 (zero overlap), the minimum possible two-tailed p-value is $2 / 252 \approx 0.00794$. For **3 vs 3**, the minimum possible p-value is $2 / \binom{6}{3} = 2 / 20 = 0.10$.
2. **Holm-Bonferroni FWER Adjustment & `includeRawSignificant`**:
   - `filterMetrics()` re-evaluates `holmBonferroni()` on the filtered hypothesis family. However, when filtering across many metrics on small sample runs ($N \le 5$), the strictest Holm-Bonferroni threshold ($\alpha / m$) can still fall below the minimum achievable permutation p-value ($0.00794$).
   - **Rule of Thumb**: When analyzing runs with fewer than 8–10 iterations per group, pass `includeRawSignificant: true` to `get_significant_changes` and inspect `analyze_test` outputs directly for:
     - Raw `pValue <= 0.05` (`rawSignificant: true`; e.g., `pValue ≈ 0.0079` on a 5v5 run means **complete separation** between the two groups).
     - Large relative `change` (e.g., `> 10%` or `> 25%`) that is consistent across `avg`, `p50`, and `p90` and across related tests.
